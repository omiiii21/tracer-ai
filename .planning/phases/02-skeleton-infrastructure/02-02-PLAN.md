The Postgres image runs `/docker-entrypoint-initdb.d/*.sql` files as the `postgres` superuser ONLY on an empty data volume (Pitfall 1). The DSN in `.env.example` is `postgresql+asyncpg://tracer:tracer@db:5432/tracer_ai` — match those credentials exactly.

```sql
-- tracer-ai db init script (D-2.09 + RESEARCH.md Pitfall 2)
-- Runs once per empty data volume as the `postgres` superuser.
-- Creates the application role with NOSUPERUSER (so the Alembic migration
-- running as `tracer` cannot CREATE EXTENSION) — extension creation is
-- this script's job, not the migration's.

-- 1. Application role (matches .env.example DATABASE_URL credentials)
DO $$
BEGIN
    IF NOT EXISTS (SELECT FROM pg_catalog.pg_roles WHERE rolname = 'tracer') THEN
        CREATE ROLE tracer
            LOGIN
            PASSWORD 'tracer'
            NOSUPERUSER
            NOCREATEROLE
            NOCREATEDB;
    END IF;
END
$$;

-- 2. Application database (owned by tracer)
SELECT 'CREATE DATABASE tracer_ai OWNER tracer'
WHERE NOT EXISTS (SELECT FROM pg_database WHERE datname = 'tracer_ai')
\gexec

-- 3. Connect into tracer_ai and enable pgvector (per D-2.09 + Pitfall 2)
\c tracer_ai
CREATE EXTENSION IF NOT EXISTS vector;

-- 4. Grant schema usage to tracer so the migration can CREATE TABLE
GRANT ALL ON SCHEMA public TO tracer;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO tracer;
```

The `\gexec` and `\c` are psql meta-commands; the Postgres image's init mechanism runs files via psql, so they work as expected. The `DO` block guards the role creation (idempotent if `init.sql` somehow runs twice — defensive).

Per Open Question Q3 (RESEARCH.md §Security Domain): the operator approves adding `USER app` to BOTH `dev` and `prod` stages. This adds ~3 lines and addresses ASVS V14 "container as non-root" — portfolio narrative wins.

The `UV_VERSION=0.5` and `PYTHON_VERSION=3.12` are ARG so a future revision can bump them; pin specific minors here. Cache mount on `/root/.cache/uv` (the deps stage RUN runs as root before USER switch). After USER switch, the venv at `/app/.venv` is owned by `app:app` so uvicorn can write `__pycache__` directories inside it.

```dockerfile
# syntax=docker/dockerfile:1.7
# Multi-stage Dockerfile for tracer-ai backend
# Per D-2.11: stages are base / deps / dev / prod (prod NOT BUILT in Phase 2; reserved per ADR 009)
# Per RESEARCH.md Topic 1: canonical uv pattern with cache mount + --no-install-project + UV_LINK_MODE=copy
# Per Open Question Q3 / ASVS V14: USER app in dev AND prod stages

ARG PYTHON_VERSION=3.12
ARG UV_VERSION=0.5

# ============================================================================
# STAGE 1: base — Python runtime + uv binary + non-root user
# ============================================================================
FROM python:${PYTHON_VERSION}-slim-bookworm AS base

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PROJECT_ENVIRONMENT=/app/.venv \
    PATH="/app/.venv/bin:${PATH}"

# System deps: curl for healthcheck (api stage uses it); ca-certs for HTTPS
RUN apt-get update && apt-get install -y --no-install-recommends \
        curl ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Install uv via Astral-published image (digest-pinned in compose; tag here is the floor)
COPY --from=ghcr.io/astral-sh/uv:${UV_VERSION} /uv /uvx /bin/

# Non-root user (uid 1000 matches typical host dev user; bind-mount file ownership stays clean)
RUN groupadd -r app -g 1000 && \
    useradd -r -u 1000 -g app -m -d /home/app -s /bin/bash app && \
    mkdir -p /app && chown -R app:app /app

WORKDIR /app

# ============================================================================
# STAGE 2: deps — install pinned dependencies (cacheable layer)
# ============================================================================
FROM base AS deps

# Mount pyproject.toml + uv.lock in (don't COPY — keeps layer cache invalidation
# tied ONLY to dep manifest changes, not source changes)
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    uv sync --frozen --no-install-project --all-extras

# /app/.venv now exists and is root-owned; chown to app for dev/prod stages
RUN chown -R app:app /app/.venv

# ============================================================================
# STAGE 3: dev — compose targets this; source bind-mounted at runtime
# ============================================================================
FROM deps AS dev

USER app
EXPOSE 8000
# Source is bind-mounted by compose at /app/tracer_ai (D-2.12); placeholder CMD here
# is overridden in compose for the api and migrate services.
CMD ["uvicorn", "tracer_ai.api.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]

# ============================================================================
# STAGE 4: prod — NOT BUILT in Phase 2; reserved per ADR 009 v1.5 deployment
# ============================================================================
FROM deps AS prod

# Copy source (no bind-mount in prod)
COPY --chown=app:app tracer_ai /app/tracer_ai
RUN --mount=type=cache,target=/root/.cache/uv \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    --mount=type=bind,source=uv.lock,target=uv.lock \
    uv sync --frozen --all-extras

USER app
EXPOSE 8000
CMD ["uvicorn", "tracer_ai.api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Note: the `dev` stage's CMD is a placeholder. The Compose `api` and `migrate` services override the command; migrations and api startup come online in Wave 3 / Wave 4. The stage still builds and is runnable.
